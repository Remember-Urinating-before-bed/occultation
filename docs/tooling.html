1The shape of a Python project

A package is a folder of Python files. A module is one file. That is the whole hierarchy.

Import

Borrowing code

from occultation.domain.observer import ObserverLocation means “go into that file and bring this name here”.

__init__.py

The “this is a folder of code” marker

A file that tells the tools a folder is a package. This repo has one in every package folder, nested ones included — see Q3.

__pycache__

Python's leftovers

Speed-up files Python writes by itself. Never edited, never committed — the ignore file hides them.

2Where the libraries live

Your project does not borrow from your laptop. It has its own private shelf of libraries.

Why bother? Two projects on one laptop can then want different versions of the same library without fighting. This is the single most important habit in Python, and this repo does it properly.

uv still makes a .venv/ — so what changed? uv is not a replacement for the idea of a virtual environment; it is a much faster, stricter tool that creates and manages one. The comparison, honestly:

venv + pipcondauv (this repo)
Makes a private shelfyes, but you activate it by handyes, its own kindyes, automatically
Installs Python itselfnoyesyes (uv python install)
Locks exact versionsnot by defaultenvironment.yml is looseyes, uv.lock, CI enforces it
Speedslowslow, heavy solverseconds
Best atnothing in particularnon-Python scientific binaries (GDAL, CUDA)pure-Python projects like this one

The honest summary: conda is not wrong, it is aimed at a different problem. This project needs one pure-Python library, so a lock file and a 2-second install beat a 500 MB solver. And the project rules forbid swapping the tool without asking first.

3One tool that does the boring parts

uv fetches Python, builds the private shelf, and installs the libraries. One command instead of five (the five are listed at the bottom of this section).

CommandWhat it does, in words
uv sync --locked --devBuild the private shelf exactly as the lock file says, including the developer tools.
uv run pytestRun something inside that shelf, without activating anything first.
uv python installFetch the right Python (3.12) if it is missing — used by CI.
uv buildPackage the project into a distributable file (dist/*.whl).

Why not just pip install? Because pip installs into whatever Python it finds and does not lock versions. The project rules forbid switching away from uv without asking, precisely so every machine and CI agree.

6What a test actually is

A test is a tiny program that says “if the code is right, this number must come out”. Nothing more.

Coverage

“How much of the code did the tests touch?”

Currently about 92%. It is a flashlight, not a grade: it shows which lines were never exercised, not whether the exercised ones are correct.

Regression test

A test that guards one published result

The Regulus case is a regression test. If a future change breaks the maths, that one test fails loudly instead of the error going unnoticed.

7Git: the undo history for a whole project

Git saves snapshots. A branch is a line of snapshots you can experiment on without disturbing the main one.

Commit

Saving a snapshot

You choose which files go in. That is why .gitignore exists — it lists things that should never be saved: the virtual environment, caches, coverage reports.

Pull request

Asking before merging

A PR says “here is my branch, please look”. CI runs the three checks on it, so a broken branch is caught before it reaches main.

8CI: a robot that runs the checks for you

Every time code is pushed, a fresh computer with nothing installed repeats the whole setup and runs the checks.

Why beginners get bitten here: a check that passes locally but fails in CI almost always means a file was never committed, or the lock file was not updated. The robot only sees what Git has.

Q1 — Why are the folders called core and domain? Is core “the core logic”, and is domain like a Java struct?

Both names come from a well-known way of organising code (the “hexagonal” or “ports and adapters” style). The split is not “important code” versus “unimportant code” — it is data shapes versus calculations:

FolderWhat lives thereIn this repo
domain/What the things are: named values, their units, and the rules for a valid value. No astronomy maths.ObserverLocation, StarOccultationElements, StarOccultationResult
core/What the project does: the formulas, implemented by this project rather than borrowed from a library.calculate_geocentric_observer, calculate_star_local_circumstances

“Core” is indeed “the core logic” — with a sharp edge: core/ holds the custom logic, the maths this project is learning to write. The reference engine (Skyfield) will be its opposite number, and core/ is forbidden to import it.

“Domain” is not like a Java struct, though it looks similar at first glance. A struct is a passive bag of fields. These are frozen dataclasses with validation:

@dataclass(frozen=True, slots=True)
class ObserverLocation:
    longitude_deg_east: float
    latitude_deg: float
    elevation_m: float

    def __post_init__(self) -> None:
        if not -180.0 <= self.longitude_deg_east <= 180.0:
            raise ValueError("longitude_deg_east must be between -180 and 180")
  • frozen=True — once created it cannot be modified (no accidental observer.latitude_deg = 99).
  • slots=True — no new fields can be bolted on at runtime, and it uses less memory.
  • __post_init__ — the object refuses to exist in an invalid state. A Java struct would happily hold latitude 999.

The closest Java analogy is therefore not struct but a record with a validating constructor: an immutable value object. The point of the folder is that every number in this project has one home, one spelling, and one set of rules — units live in the field names (_deg_east, _m, _earth_radii) so a reader can never confuse degrees with radians.

Q2 — ObserverLocation is east-positive, but Meeus (and the fixture) use west-positive longitude. Where is the conversion?

Your reading is correct on both counts, and the conversion is real — it is written as a sign flip inside the formula rather than as a separate “convert” function.

Meeus writes the local hour angle as H = H0 + H1·t − λ − ΔT/239.345, where his λ is west-positive. The project stores east-positive longitude, so − λ_west = + longitude_deg_east, and the term becomes a plus. That is the whole conversion, documented at the exact line that performs it (core/local_circumstances.py):

def _local_hour_angle_deg(...) -> float:
    """Return H = H0 + H1 t - lambda - Delta T / 239.345 in degrees.

    Meeus writes ``- lambda`` where lambda is the *west*-positive longitude;
    our domain uses the conventional east-positive longitude, so that term
    becomes ``+ longitude_deg_east``.
    """
    return (
        elements.greenwich_hour_angle_at_reference_deg
        + elements.greenwich_hour_angle_rate_deg_per_hour * hours_after_reference
        + longitude_deg_east                    # <-- the sign flip lives here
        - delta_t_seconds / DELTA_T_SECONDS_PER_DEGREE_OF_HOUR_ANGLE
    )

The fixture performs the same flip on the input side, in a comment a human reads:

# Project convention: east positive. Meeus prints 116.8640 degrees west.
longitude_deg_east = -116.8640

Two reasons it is done this way instead of with a west_to_east() helper:

  • One convention everywhere. The handoff rule is “east-positive longitude everywhere in code; convert at the boundary”. The boundary here is the printed page, read by a human, so the human flips the sign once and writes the comment.
  • A helper would hide the arithmetic. A function that only negates a number adds a name without adding meaning, and it would move the − λ → + λ step away from the formula it belongs to. The docstring plus the regression test are the safety net.

How to prove it: the regression test feeds the flipped value and reproduces Meeus's printed answers (Δ = 1.152556, P = 24.6654°, h = 42.6499°). A sign handled wrongly would move the altitude and the separation away from the book. The test is the conversion's proof.

Q3 — Why is there an __init__.py in both domain/ and core/? Does that mean three packages?

Yes — three packages, and that is intentional. Packages nest: occultation is a package, and occultation.domain and occultation.core are packages inside it. Every folder that should be importable carries its own marker file.

FileIts contents hereWhat it declares
src/occultation/__init__.pya docstring (176 bytes)“occultation is a package”
src/occultation/domain/__init__.pya docstring (58 bytes)“occultation.domain is a package”
src/occultation/core/__init__.pya docstring (69 bytes)“occultation.core is a package”

Two details worth knowing:

  • They are not empty here. Each holds a one-line docstring, so help(occultation.core) says what the folder is for. Empty is also legal, and older tutorials say “empty file”; this repo prefers the docstring.
  • They are not the only way any more. Modern Python also allows a “namespace package” (a folder with no __init__.py). This repo does not use that, and the handoff treats the marker file as the convention — so keep adding one to every new package folder.

The practical consequence: import occultation.core.local_circumstances works only because every folder along that path is a package. Delete one __init__.py and the import breaks.

Q4 — Which five commands does uv combine into one, and what is the benefit over conda or plain venv if uv still creates a .venv?

The six are listed in section 2 above; in one line each:

Without uvWhat it was doing
python3 -m venv .venvcreate the private shelf
source .venv/bin/activateremember to use it in this terminal
pip install -e .install this project into it
pip install pytest-cov ruff mypyinstall the developer tools
pip freeze > requirements.txtwrite down what got installed, by hand
(pyenv / brew / manual download)get Python 3.12 in the first place

uv sync --locked --dev performs all of the first five, and uv run <command> removes the need for activate entirely: it runs the command inside the shelf without changing your shell. Fewer steps also means fewer ways to end up with a different environment than CI.

Why the .venv still exists — and why that is the point. uv does not replace the idea of a virtual environment; it replaces the chores around one. The .venv/ is what keeps the project's libraries separate from your laptop's system Python, and that separation is the thing you actually want. What uv adds on top:

  • A lock file. uv.lock (603 lines, 21 packages here) records the exact version of every library, indirect ones included. CI runs with --locked, so a version cannot drift unnoticed. pip freeze writes a list too, but nothing verifies it and nothing enforces it.
  • It manages Python itself. uv python install fetches CPython 3.12.14; with venv you must install Python some other way first.
  • Speed and no activation. Seconds, and uv run always uses the right interpreter.

uv versus conda: conda is not wrong, it answers a different question. Its real strength is shipping non-Python compiled libraries (GDAL, CUDA, compilers) as binaries. This project needs exactly one pure-Python runtime dependency (skyfield), so a lock file and a two-second sync fit better than a large solver and a second package ecosystem. Switching tools is also explicitly forbidden without asking first — reproducibility across laptop and CI is worth more here than personal preference.

Q5 — What does mypy actually do? Python is dynamically typed, so a declared return type can still be violated at runtime.

Your premise is exactly right and it is the key to understanding mypy: mypy does not run your code and it enforces nothing at runtime. It is a spell-checker for types. It reads the source, reasons about what each name can hold, and complains before anything runs. Python itself will still happily return the wrong type at 3 a.m.; mypy's job is to make that mistake impossible to write without a red squiggle.

A concrete example. Suppose someone edits the observer conversion and returns a string by accident:

def calculate_geocentric_observer(
    observer: ObserverLocation,
) -> GeocentricObserverCoordinates:
    ...
    return "rho sin phi' = 0.83"        # wrong type, but perfectly valid Python

Running it changes nothing: the function returns a string, and the crash happens later, far from the cause. mypy points at the line immediately:

error: Incompatible return value type
       (got "str", expected "GeocentricObserverCoordinates")  [return-value]

Two more examples of the same idea, both in this repo's style:

  • Wrong value is not a type error. longitude_deg_east = "114.17" (a string) is caught by mypy. But longitude_deg_east = 114.17 when the field means west-positive degrees is not caught — mypy knows float, it does not know “degrees west”. That is why units live in the field names and why the tests exist: types catch shape, tests catch meaning.
  • It forces the “impossible” branch to be handled. In local_circumstances.py the solver holds relative_motion: RelativeMotion | None while looping, then uses it after the loop. mypy insists the code prove the None case cannot reach that line; without the annotation it would have to guess, and guessing is where bugs hide.

What it buys this project: the domain layer is a set of small value objects passed between functions, so a wrong-shaped value is the most likely mistake. mypy catches that class of mistake for free on every commit. What it cannot buy is correct astronomy — a formula can be type-perfect and physically wrong, and only the Meeus regression test catches that.

Try it yourself: uv run mypy src (clean in this repo today).

Q6 — What is data/ for, and is reference/ referenced anywhere? How would this be used technically?

data/ is the project's filing cabinet for external scientific data. Nothing in it is generated by the code; everything in it is obtained, and the rules are strict (handoff §3.3):

PathPurposeState today
data/README.mdExplains the folder and the manifest ruleexists
data/manifest.jsonOne entry per dataset: source, version, date obtained, coverage, checksum, licenceexists, but declares zero datasets
data/external/Local ephemeris files, e.g. de440s.bsp (1849–2150, 32 MB)does not exist yet
data/coefficients/Textbook coefficient tables kept as versioned dataplanned
data/validation/HKO / Occult extracts used as comparison targetsplanned

What makes it more than a folder: no runtime download (an ephemeris must never appear silently at startup), the file must be fetched by a deliberate separate step, its path must be explicit (data/external/de440s.bsp), and large files belong in an artifact store or Git LFS rather than normal Git history. Today the active work-package needs none of it: Meeus's method takes the Besselian elements as inputs copied from the printed tables, so there is no ephemeris to fetch.

Is reference/ referenced anywhere? No — and that is deliberate. Searching the tree for reference finds only documentation and the test folder name tests/reference_cases/, which means “cases taken from the reference book”, not “the reference engine”. Concretely:

  • src/occultation/reference/ does not exist, nothing imports Skyfield, and the single declared runtime dependency is unused so far.
  • The handoff (§3.4) plans it as reference/skyfield_engine.py, added at milestone 1.
  • The rule is one-way: core/ may never import occultation.reference. The reference engine may be a dependency of the comparison layer and of the application, never of the custom maths.

The intended technical usage, in order (handoff §3.2, §5.1, §11):

  1. Now: the custom core computes from supplied elements, and the Meeus worked example is the oracle. No Skyfield, no data files.
  2. Milestone 1: add reference/skyfield_engine.py plus a local ephemeris fetched by scripts/fetch_reference_data.py and checked against data/manifest.json by scripts/verify_reference_data.py.
  3. Then: the comparison layer runs both engines on identical inputs and emits machine-readable differences (event_type,date,custom_time,reference_time,error_seconds) with max / median / 95th-percentile error and the known reasons for differences.
  4. Later: product-level validation against Hong Kong Observatory output (converted to Asia/Hong_Kong) and against Occult v4; then reference-engine responsibilities are replaced incrementally, while Skyfield stays available as an independent regression oracle.

So the boundary is not decoration: it is what lets the project prove its own maths against a trusted engine, then retire that engine, without ever letting the two definitions of “correct” blur together.
